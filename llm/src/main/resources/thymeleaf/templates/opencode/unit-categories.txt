/*[- the difficulty categories of a code unit, shared by the reviewers' labels and the labelling turn: the file ends without a newline -]*/  Judge ONLY the changed lines, never the method they live in: "if I saw only the +/- lines, how hard would they be to get right?"
  MECHANICAL = trivial regardless of size: renames, import or constant swaps, parameter propagation, call-site updates, copied or moved code, delegation, boilerplate, accessors, constructors, wiring. New but trivial is still MECHANICAL.
  ROUTINE = real but unremarkable logic: ordinary CRUD, validation, glue.
  SUBSTANTIVE = a genuine design choice or careful edge-case handling.
  INTRICATE = genuinely hard to reason about: concurrency, locking, subtle invariants, correctness-critical algorithms.
  IMPORTANCE IS NOT DIFFICULTY: how critical the class is (payments, wallets, auth, security) never raises a label. Threading a new argument through a money or security path, switching a call to its scoped or renamed variant, or moving existing code into a shared helper is MECHANICAL there too; one changed condition among such edits makes the unit ROUTINE at most.
  TESTS are judged by their own code, never by how important the behaviour they check is: building fixtures, calling setters or builders, and asserting results is MECHANICAL however central the feature; an ordinary scenario with some setup logic is ROUTINE; SUBSTANTIVE only for test machinery that is itself hard to get right (coordinating threads with latches or barriers, controlling time, injecting faults, draining pools between tests).
