You coordinate the code review of one commit in the git repository in the current directory. Find out what the commit changed with read-only git commands (for example `git show --stat <sha>`); do not read the full diff yourself.

Plan the work as AT MOST 8 codiqo-module-reviewer subagent tasks, splitting by module or directory. Give large or central areas a task each; group small areas changed in the same way into one task and say what they have in common. Launch all tasks in ONE response as parallel subagent tool calls WITHOUT background (foreground calls return each report directly). Each prompt names the commit, its purpose and the exact paths to review. Never call a subagent again just to ask for its status.

Review only what this commit changes. A defect that already existed before the commit in code it touches is not a finding of this commit.

If a subagent's report holds no JSON object, its area went unreviewed: start ONE more subagent for those paths (split them in two if the area was large) before merging; never more than one retry per area.

Severity follows certainty and harm, as Codiqo's scoring has always graded it. "blocking": you traced the defect through the code and it will cause incorrect behaviour in normal use: a security hole, data loss or corruption, a race or deadlock, a crash or failed start on a normal path, a build that no longer compiles, a wrong amount of money or a wrong business result. "major": a real defect that needs particular conditions to show, or whose effect is limited and recoverable, or one you strongly suspect but cannot fully confirm because context is missing. "minor": a low-impact edge case. Never lower a traced, certain defect to major because the fix looks small. When you merge, keep the most severe grading a subagent gave a confirmed defect.

When all subagents have reported: merge their findings, drop duplicates (the same defect repeated across similar areas becomes one finding listing the affected files), drop anything speculative, stylistic or about documentation only, and verify any finding you doubt by reading the cited code. Then answer with one JSON object and nothing else:
{"tasks":[{"paths":[...],"findings":<count>}],"blocking":[BUG],"major":[BUG],"minor":[BUG]}
BUG is {"type":"SECURITY|CONCURRENCY|DATA_CORRUPTION|LOGIC|RESOURCE_LEAK|NULL_POINTER|ARCHITECTURE|OTHER","title":"...","description":"what is wrong, the input or path that triggers it, and the lines you checked as File.java:line","file":"repository-relative path","line":"new-file line number, as a JSON number","confidence":"HIGH|MEDIUM","suggestedFix":"one line","suggestedFileFix":"how to fix it"}. blocking = will break production or corrupt data; major = real defect with limited impact; minor = small real defect. Empty arrays are the right answer when nothing is wrong.

JSON RULES: the answer is read by a program, and malformed JSON loses the whole review.
1. The answer is one JSON object and nothing else: no markdown code fences, no text before or after it.
2. Every field name is double-quoted; no trailing commas; every array element is a complete object, never null.
3. Leave an optional field out rather than writing null; an empty array is the right value when nothing was found.
4. Inside strings a backslash may only come before one of " \ / n r t b f u. Write a newline as \n, a quote in code as \", a backslash in code as \; a regex such as \s is written \\s.
5. Describe a fix in words rather than quoting code that contains quotes or backslashes.
6. Write all text in English.

STEP BUDGET: you have at most 40 steps. Stop calling tools by step 37 at the latest and always finish with the JSON answer; an unfinished review is worth nothing.
